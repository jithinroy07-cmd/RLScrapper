# UAE Real Estate Scraper: design contract (Dubai + Sharjah)

Status: contract for the first build, written 25 Oct 2026 from `docs/research-2026-10-25.md` (read the Correction block at the top of that note first: it is the record of a one-off exploratory session, not a data source for this project, and it holds no property-portal data).
Every module is built against this file. If code and this file disagree, fix one of them in the same change.

This is a **standalone project**, modelled on an earlier scraper built for another market: its own git repo, its own Google Cloud project / service account / spreadsheet, its own API keys. Nothing is carried over from that project except code that has been reviewed and adapted. Never copy in: `.env`, service-account JSON, `.git`, any registry dump, seed list, `geocode_cache.json`, `pins.geojson`, or hardcoded project lists.

## 0. Principles (these override convenience)

1. **Blank beats invented.** No default developer, price, bedrooms, handover, id or location. An unknown value is an empty cell. Every price / bedroom / handover value in `Listing_Data` carries the URL it came from.
2. **Fail loud.** A source that errors, returns zero rows, or returns far fewer rows than last run makes the run exit non-zero. There is no fallback to a bundled snapshot. A green run must mean fresh data, with one explicit exception: a source that is not configured is skipped, not failed, unless it is named in `REQUIRE_SOURCES`. So a run with no source configured at all is green and changes nothing; it logs a loud `NO SOURCE PRODUCED ANY REGISTRY ROW` warning, and `REQUIRE_SOURCES=dld_projects` is how the owner makes that case fail.
3. **Namespaced identity.** Dubai and Sharjah ids can never collide or merge.
4. **Legitimate sources only.** Official open data, licensed APIs, and developer pages whose terms allow it. No scraping of sites whose terms forbid automated access, no spoofed browser User-Agent, no `verify=False`, no bypassing 403 / Cloudflare / captcha walls.
5. **Location precision is data.** A pin that is only a community centroid must never look like an exact pin.
6. **Private by default.** The public map is a separate, deliberate decision (see section 10).

## 1. Scope

- Emirates: `Dubai`, `Sharjah` only (`EMIRATES = ("Dubai", "Sharjah")`). Other emirates are out of scope and rows for them are dropped with a log line.
- The **emirate of a project comes from the source registry** (DLD means Dubai, SRERD means Sharjah), never from its coordinates. Coordinates are validated against the emirate, not used to decide it.
- Currency AED (integers, no decimals). Area unit sq ft. Display time zone `Asia/Dubai` (UTC+4); all stored timestamps are timezone-aware UTC ISO-8601 (`2026-10-25T03:00:00Z`); dates are `YYYY-MM-DD`.

## 2. Identity

A project has one or more **keys**. `RegistryRow.identity_keys() -> list[str]`:

| Key | Format | Validation |
|---|---|---|
| DLD | `dld:dubai:<project_number>` | project number matches `^\d{1,9}$` |
| SRERD | `srerd:sharjah:<id>` | id matches `^[A-Za-z0-9._-]{1,40}$` |
| Name (fallback only when no registry id) | `name:<emirate-lower>:<developer-slug>:<project-slug>` | both the developer and the project name give a usable slug (next rule) |

Rules:
- Slugs: Unicode NFKD, strip diacritics, other scripts' decimal digits folded to ASCII (so `Tower ١` and `Tower ٢` stay apart), `&` read as `and`, lowercase, ASCII alphanumerics only joined by `-` (`models.slugify`). A name may become a key part (`models.identity_slug`) only if its slug holds an ASCII letter and slugifying would not silently throw something away: a name written only in Arabic yields no key part, even when it contains digits (otherwise `برج ١` and `مشروع ١` of one developer would both become `1` and merge); so does a name holding a letter or number from another script that survives the folding (Arabic, Devanagari, CJK, or a Latin letter that does not decompose, such as the o-stroke or the sharp s), because two names that differ only by it would slug alike; and so does a name holding `+`, `#` or `@` (`Tower A+` and `Tower A`, `C#` and `C`). Ordinary punctuation, diacritics that fold and Unicode modifier letters (the hamza and ayn marks of Arabic transliteration, category Lm, treated as punctuation) never distinguish projects and still key. Nothing is invented in place of a missing key part (no hash, no transliteration): the row is keyed by its registry id if it has one, otherwise it has no identity. The adapters and `main` count and refuse such a row, and the dedupe code never merges it or drops it silently. The reason the adapters count it under (`R_NO_IDENTITY`) is a fixed text that states this rule (the developer and the project name must each have a Latin letter, no letter or number from another script, and none of `+ # @`; a DLD or SRERD row is exempt only when it carries a usable registry id) and never the name itself. The Arabic name is never part of a key.
- **Do not strip tower / block / part letters** for identity (`Tower A` and `Tower B` are different projects). Trailing `phase N` / `stage N` may be stripped for the *geocode query only*, never for identity.
- An advertising permit number (Dubai Trakheesi etc.) identifies an advertisement, not a project. It is stored in `Permit No.` and is **never** a key.
- Matching: two rows are the same project if they share any key. Exception: if both rows carry a registry key of the same authority and those keys differ, they are different projects even if their name keys match.
- Never default an id. An unknown id is `None`; a placeholder-looking value (`n/a`, `tbc`, `-`, `0`, `unknown`, `null`, empty) is treated as `None` (explicit blocklist in `models.py`).
- There is no length rule on ids (short numeric DLD ids are valid).

## 3. Data model (Google Sheet tabs)

All sheet access is by **header name** through one `HEADERS` mapping per tab in `src/gsheet_manager.py`. No positional column letters or `row[7]` anywhere. Adding a column must not break existing ones.

Tabs: `Registry_Projects`, `Listing_Data`, `Launch_Candidates`, `Map_Pins`, `Geocode_Overrides`, `Scrape_Run_Logs`.

### Registry_Projects (rows from official registries; source of truth for ids)

`Project Key` (primary key: the first of identity_keys) , `Emirate`, `Registry` (`DLD` | `SRERD` | `SEED`), `Registry Project No.`, `Project Name (EN)`, `Project Name (AR)`, `Developer`, `Master Developer`, `Master Project`, `Area (EN)`, `Area (AR)`, `Zone`, `Status`, `Percent Completed`, `Start Date`, `Completion Date`, `Cancellation Date`, `Escrow Agent`, `Units`, `Buildings`, `Villas`, `Permit No.`, `Source Dataset`, `Source Refreshed`, `First Seen`, `Last Seen`, `Latitude`, `Longitude`, `Location Precision` (`exact` | `community` | `area` | blank), `Geocode Method`, `Geocode Status`, `Map Pin Link`.

Columns a person adds to the tab by hand (names the code does not know) are carried across every rewrite as plain values, matched by the stored `Project Key` against any key of the new rows; a value whose key no longer exists cannot follow anything and is reported in a warning, never silently dropped.

Who edits `Registry_Projects`: the run owns it. Every run rewrites all data rows from the merge of fresh source rows and the rows already in the tab, and **fresh wins**: any cell the feed fills with a non-empty value replaces what is in the sheet, so a hand correction to such a cell is reverted on the next run without a warning. What does survive: a cell the feed leaves blank (a person may fill it), a row no feed mentions (nothing is ever deleted by a run), and coordinates already present. The supported ways to correct something are `Geocode_Overrides` for a pin, and the seed CSV for a `SEED` row (a `SEED` row has no registry id, so its key is built from name and developer: renaming it in the sheet makes the next run see the CSV row as a new project and add a second one). A row typed into the tab by hand is kept and is merged with a feed row when they share a key.

Dubai DLD project field mapping (legacy Dubai Pulse schema, confirmed from archived copies; the live Data.Dubai API column names are **not verified**, so the adapter must accept both the snake_case names below and the upper-case DLD portal names and fail loudly on missing required ones):
`project_number`, `project_name`(/`PROJECT_EN`), `developer_name`, `master_developer_name`, `project_start_date`, `project_end_date`, `completion_date`, `cancellation_date`, `project_status`, `percent_completed`, `escrow_agent_name`, `area_name_en`, `area_name_ar`, `master_project_en`, `zoning_authority_en`, `no_of_lands`, `no_of_buildings`, `no_of_villas`, `no_of_units`. Source dates are `dd-mm-yyyy` in the legacy CSV; normalise to ISO.

### Listing_Data (commercial facts; keyed by `Project Key`; agents/analysts own it)

`Project Key`, `Price From (AED)`, `Price To (AED)`, `Price per sq ft (AED)`, `Area From (sq ft)`, `Area To (sq ft)`, `Bedrooms Min`, `Bedrooms Max`, `Property Types`, `Handover`, `Payment Plan`, `Source URL` (**required**; rows without it are rejected), `Source Licence` (`licensed-api` | `developer-permitted` | `manual`), `As Of`, `Entered By`.
The seed file `src/data/seed_projects.csv` is applied each run and **never overwrites** a row an analyst edited; the latest row per key wins. A seed row needs a valid namespaced Project Key and an http(s) `Source URL`; a row without either is not added, and the run exits 1 with a fixed message that names the field and the seed row number, never the cell (the run goes on and adds the good rows). When the map reads `Listing_Data`, a row with an invalid key or no http(s) `Source URL` is skipped and counted. A typed price, area or bedroom cell that the parsers (section 6) refuse is left blank rather than guessed, and the refusals are counted in the log (a count, never the text).
A row joins a project on ANY of the project's identity keys, but a `name:` key is only as stable as the developer and project names the feed gives: when a feed renames the project, the old `name:` key stops matching and the row's facts drop off the map without any error. Analysts should re-key a row to the registry key (`dld:dubai:<number>`) once the project has one. The one exception is a `name:` key that several different registry projects share (DESIGN section 2: different registry keys of one authority mean different projects): such a name key joins none of them on the map, because it cannot be said to describe either; re-key the row to the registry key of the project it means. The run counts the unmatched `Listing_Data` keys in its log and lists up to ten of them in the `Notes` of `Scrape_Run_Logs` (the keys carry developer and project names, so they stay out of the public Actions log); it is informational, never a failure, because a seed row may legitimately lead its registry row.

### Launch_Candidates (leads from grounded AI search; never promoted automatically)

`Candidate Key`, `Emirate`, `Project Name`, `Developer`, `Area`, `Claim` (what the source says), `Source URL` (required), `Found At`, `Status` (`new` | `confirmed` | `rejected`). The key is computed, never read back from the sheet: `cand:<emirate-lower>:<developer-slug, or unknown>:<project-slug>`, and it is never a registry key. A candidate needs an emirate of Dubai or Sharjah, an http(s) `Source URL`, and a project name that gives a usable slug (the same rule as a name key, section 2); anything else is discarded.

### Geocode_Overrides (a human pin always wins; never auto-overwritten)

`Project Key`, `Latitude`, `Longitude`, `Precision`, `Note`.

### Map_Pins and Scrape_Run_Logs

`Map_Pins`: only rows with real coordinates, `exact` first. `Scrape_Run_Logs`: one row per run: UTC start/end, per-source row counts and status, geocode stats, exit status, git sha if available. The run reads its own earlier rows back to find the row count of each source's last good run (the baseline of the row-drop guard); a `Sources` cell that is not a JSON object, or an entry in it without a known status and a whole, non-negative row count, is ignored with a warning that gives the tab, the row number and, for an entry, its position, never the source name (the cell is hand-editable and the log is public). Only the names in `config.SOURCE_NAMES` (`dld_projects`, `srerd_projects`, `seed_csv`, `gemini_news`) are kept from that cell, in the sheet reader and again in `main`; entries for any other name are counted in one INFO line and never named.

## 4. Source adapters (`src/sources/`)

```python
class SourceError(Exception): ...          # any failure; never swallowed

@dataclass
class SourceResult:
    source: str                 # adapter name
    rows: list[RegistryRow]
    fetched_at: str             # UTC ISO
    source_refreshed: str | None
    notes: list[str]

class SourceAdapter(Protocol):
    name: str
    def enabled(self, cfg) -> bool: ...
    def fetch(self) -> SourceResult: ...   # raises SourceError
```

| Adapter | Source | Status |
|---|---|---|
| `dld_projects` | Data.Dubai open API `https://apis.data.dubai/open/dld/dld_projects-open-api` (limit / offset paging). Needs a free Data.Dubai account key + secret (`DATA_DUBAI_API_KEY`, `DATA_DUBAI_API_SECRET`), client-credentials token (requested from the separate host `api.dubaipulse.gov.ae`, while the data is read from `apis.data.dubai`), Bearer header. Paging ends at an empty page: a page that looks final (stated total reached, or fewer rows than asked) is followed by one confirming request; if that request fails the rows already collected are kept and a note says the end was not confirmed. **Not tested against the live API** (no key yet). Published monthly, so the daily run mostly re-confirms. Optional change detection via the anonymous catalogue `https://data.dubai/o/c/datasets` (dataset 467654 `dateModified`; always pass `fields=`, use long timeouts). | built against documented schema + synthetic fixtures; live-untested |
| `srerd_projects` | Sharjah Registration Department "List of Projects" page, POST `cms-proxy.shjrerd.gov.ae/api/Projects/GetProjects`; columns name AR/EN, area AR/EN, ownership type only. **Disabled by default** (`ENABLE_SRERD=true`); response shape unverified, so the parser is tolerant and the adapter raises `SourceError` on any shape it does not recognise. | unverified |
| `seed_csv` | `src/data/seed_registry.csv`: hand-researched **registry** rows (SEED registry), columns `Emirate`, `Project Name (EN)`, `Developer`, `Master Developer`, `Master Project`, `Area (EN)`, `Zone`, `Status`, `Completion Date`, `Source URL`. `Source URL` is required per row and is stored in `Source Dataset`. May legitimately contain zero rows (ships header-only). A header that lacks a required column is a `SourceError` naming only the missing layout columns and the header's cell count, and extra columns are ignored with a count: the text of a header cell is never logged, because a file saved without its header row has a data row there. Not to be confused with `src/data/seed_projects.csv`, which is the **Listing_Data** seed (section 3). | built |
| `gemini_news` | Gemini with Google Search grounding, **grounded only**. A lead is kept only if its `Source URL` is http(s) without embedded credentials and belongs to a page the search tool actually retrieved (the address is one of the grounding sources the response lists, or its host is the same site as one of them); everything else is discarded and counted. That proves the site was retrieved, not that the page says what the lead claims, which is why candidates stay `new` until a person confirms them. A response that proposes leads but carries no grounding at all is a `SourceError`. Writes `Launch_Candidates` only. Disabled by default (`ENABLE_GEMINI_NEWS=true`). The model name comes from `GEMINI_MODEL` with **no hardcoded default** (a default model name could not be verified, so none is shipped). | built |

Run semantics (`src/main.py`):
- Every enabled adapter runs; one failure does not stop the others, but the **final exit code is non-zero if any enabled adapter failed**, any adapter named in `REQUIRE_SOURCES` was skipped, or the geocode stage crashed or gave up for a reason other than a quota.
- **Row-count regression guard:** a source that **expects rows** (`dld_projects`, `srerd_projects`) returning fewer than 80 percent of its previous successful run's row count raises `SourceError` unless `ALLOW_ROW_DROP=true`; zero rows from such a source is always an error. Sources that may legitimately be empty or are edited by hand (`seed_csv`, `gemini_news`) are exempt from the shrink check: pruning the seed file must not turn every later run red. A shrink deletes nothing either way; a project that no feed mentions is kept.
- A source with no credentials configured logs `SKIPPED (not configured)` (not an error unless in `REQUIRE_SOURCES`).
- Merge: union-find over identity keys (the same approach as the earlier scraper's `dedupe`), prefer non-empty values, never invent.

## 5. Geocoding (`src/geocoder.py`, `src/emirates.py`)

Measured 25 Oct 2026 (public Nominatim, 36 names, the better of 2 phrasings each): 42 percent plausible overall; 67 percent for master communities, **7 percent (1 of 15) for single off-plan projects**; without `countrycodes=ae`, 9 of 36 bare-name queries (25 percent) returned a wrong hit, 8 of the 9 outside the UAE. Caveat: an exploratory one-off on a sample of 36 public project names that mixes recent launches with well-known communities, judged by hand against reference points that are not kept (`docs/research-2026-10-25.md` records it, and nothing in this repository reads it); it is not reproducible from here and not a registry-wide rate, so read it as the reason for the validation rules below, not as a benchmark. Therefore:

Tiers, tried in order until one passes validation; the winning tier sets `Location Precision`:
1. `exact`: query the project name (variants below).
2. `community`: query `Master Project` (else the community).
3. `area`: query `Area (EN)`.

Query rules:
- Always `countrycodes=ae`, `accept-language=en`, and append `, <Emirate>, UAE`. An empty result is better than a wrong one.
- Variants for tier 1, at most 3 per project: as given; with a trailing `by <developer>` removed (and, once, appended); with trailing `phase|stage <N>` removed. Alias table (`src/data/area_aliases.json`): Jumeirah/Jumeira, Al/El, Muwaileh/Muweilah/Muwailih, Maryam/Mariam, etc., applied before querying.
- Reject a hit (every tier) if: its coordinates do not parse (`bad-coordinates`) or the item has an unexpected shape (`bad-shape`); the provider states a country other than the UAE (`wrong-country`); it is a street (`street`: OSM class `highway`, Geoapify `street`, Google `route`); it is a whole emirate or country (`emirate-or-country`); Google flags it a partial match (`partial-match`); the provider's state is not the declared emirate (`wrong-state`); or the point is not strictly inside the declared emirate's **polygon** (`outside-emirate`). A rejected hit is a miss, not a pin. Further checks on the `exact` tier only (see the `src/geocoder.py` docstring for the full list): a hit that is a whole settlement or district (an OSM city, town, suburb or district, or an administrative boundary) is an area centroid, not a project, and is refused as exact (`coarse-for-exact`); the place the provider names must share its distinctive words with the row's own name (`name-mismatch`); a Geoapify answer that matched only a street, postcode, city or country is refused (`coarse-match`); when the row declares a community or area whose centroid cannot be obtained, the exact hit is refused rather than filed unverified (`no-centroid`); a hit more than 8 km from that centroid is refused (`far-from-community`); and a hit within 10 m of it is the community itself and is refused as exact (`is-community-centroid`). A row that declares neither a community nor an area has no centroid to check, and the exact hit stands once the other checks pass.
- HTTP 404 means "nothing matched" for LocationIQ only. For every other backend it means a wrong URL or a broken proxy: it is retried, then treated as inconclusive, never cached as "no such place", and no row is marked unresolved because of it.
- A `Geocode_Overrides` row is matched on any identity key of a project, except a `name:` key shared by several different registry projects: that is ambiguous and pins none of them. An override is not rejected for lying outside the project's emirate (a human pin wins): the run applies it and logs a warning with a count. The map export, however, drops such a pin (section 7).
- The default pacing follows the public Nominatim usage policy (read 25 Oct 2026): at most 1 request per second, and 4 requests per minute for scripts that run at regular intervals. The `nominatim` backend therefore waits 15 s between requests (counted from the start of the previous one, retries included) and stops after 200 lookups a run. That is at most 200 projects a day and fewer in practice, because one project can need several lookups (up to three name variants, then the community, then the area, plus the lookup of the centre of its community or area that an answer is checked against; centres are remembered within a run). The real figure has not been measured. The time budget (`GEOCODE_TIME_BUDGET_SECONDS`) defaults to 3300 s, 55 minutes: 200 lookups paced 15 s apart take 50 minutes. A larger value is clamped to a ceiling of 4500 s (75 minutes; the warning `GEOCODE_TIME_BUDGET_SECONDS is above the maximum 4500; using 4500` names the setting and the ceiling, never what was typed), so a typed value cannot outrun the 90-minute job limit; `tests/test_config.py` reads that limit from the workflow and keeps both numbers at least ten minutes under it. Going faster means a keyed backend (below) or a self-hosted instance. **Owner decision (open):** which keyed backend, if any.
- A geocoder abort ends the stage, not the run. When the reason is only a quota (HTTP 429, Google `OVER_QUERY_LIMIT` / `OVER_DAILY_LIMIT`) it is logged as a warning, the untried rows stay blank for tomorrow, and the exit code stays 0. Any other reason (a refused or revoked key, a plan that must be paid, five failed lookups in a row) is a failure: logged as an error and exit 1, because the pins stop coming until a person acts. The abort line names the HTTP status or Google's status token and one fixed phrase ("the key or plan was refused; check the API key", "the provider's rate limit or quota is spent"), never the provider's own words: a 429 body or Google's `error_message` can echo the query, and a query is a project name. A failed progress flush is logged as the exception class only, because the Sheets error text can echo what was written.
- Points within 1.5 km of the other emirate's polygon get `Geocode Status` suffix `border-check`.

`src/emirates.py` (bundled OSM admin polygons: Dubai relation 3766483, Sharjah relation 3766486, ODbL attribution): `emirate_for_point(lat, lon) -> "Dubai" | "Sharjah" | None`, `point_in_emirate(lat, lon, emirate) -> bool`, `distance_to_border_km(lat, lon, emirate) -> float`, `UNION_BBOX` as a coarse sanity gate only (24.62..25.70 N, 53.98..56.60 E: the rounded union of the two emirates' OSM boxes, and the only bounding box this project ships). Bounding boxes must never decide the emirate: they overlap about 85 percent.

Backends (shared machinery: budgets, 429 abort, never-tried-first queue, cooldown, flush): `nominatim` (default, public instance: one request per 15 s, 200 lookups per run, identifying User-Agent from `GEOCODE_USER_AGENT` + optional `GEOCODE_CONTACT`), `locationiq`, `geoapify` (free keys), `google` (**opt-in only** via `GEOCODE_BACKEND=google`; its terms restrict storing results, so it is never auto-selected). All of them read OpenStreetMap or an equivalent; do not expect more than the measured rates above. `Geocode_Overrides` wins over any backend.

State lives in the sheet (`Geocode Status`: `resolved via <backend> <tier> YYYY-MM-DD` / `unresolved YYYY-MM-DD`).

## 6. Parsing and units (`src/listing_data.py`)

- `parse_price_aed(text) -> int | None`: accepts `AED 1.2M`, `1.2 million`, `850K`, `Dhs 1,250,000`, `1,250,000`, `from AED 850,000`; **a comma is a thousands separator**; `M`/`million`, `K`/`thousand`; anything ambiguous returns `None`. Never scale a bare number.
- **A lone dot before exactly three digits is refused** (`750.000`, `1.200 sq ft`, `12.345`): a European writer means a thousands separator, an English one a decimal, nothing in the cell says which, and either guess is wrong by a factor of a thousand for somebody. A unit settles it (`1.250 M` is 1,250,000), as does a thousands comma (`1,250.000`) or any other digit count (`750.00`, `1250.000`). A typed number cell that is refused is counted in the run log (a count, never the text) and shows as blank on the map.
- Digits written in another script are read by value: fullwidth digits fold to ASCII (NFKC) and Arabic-Indic digits are read as the digits they are (`١٢٠٠ sq ft` is 1200). The Arabic decimal separator (`٫`) is not understood, so a cell that uses it is refused rather than misread.
- `parse_bedrooms(text) -> (min, max) | None`: `Studio` = 0, `1BR`, `2 BR`, `3 Bedroom(s)`, `4 BHK` accepted, ranges `1-3 BR`, `Studio to 3BR`; `maid` rooms ignored.
- `parse_area_sqft(text)`: sq ft canonical; sq m converted with 10.7639.
- **A bound refuses the whole cell.** A comparison or bound symbol (`<`, `>`, `=`, and the Unicode less-or-equal, greater-or-equal, not-equal and plus-minus signs; full-width forms are folded to these first) makes the cell `None` in every parser: `<3 BR` is not 3 and `< 1,250,000` is not the price, because dropping the symbol would publish a limit as if it were the figure. For bedrooms and area the same goes for a `+`, dash or slash left dangling beside the number (`3 BR /`, `3+`, `1,200 -`, `1,200+ sq ft`). A price, total or per sq ft, is the one exception: a trailing `+`, `onwards` or leading `from` reads as the From figure (`1,250,000+`, `from AED 850,000`, `1,800+`), because that is what the From column holds. A range belongs in the From and To columns, never in one cell.
- Types: `Apartment`, `Villa`, `Townhouse`, `Penthouse`, `Duplex`, `Hotel Apartment`, `Plot`, `Commercial`, `Mixed Use`, `Unknown`. `type_from_name` is strict: `Unknown` beats a wrong guess; the word `Tower` never implies Commercial.
- Price per sq ft and total price are separate fields; never convert one into the other.

## 7. Map (`site/index.html`, `scripts/export_map_pins.py`)

Leaflet + markercluster from cdnjs, OSM tiles with attribution (public tile usage policy applies), centred about 25.2 N, 55.3 E, zoom 9. Features: emirate toggle (Dubai / Sharjah), search by project / developer / registry number, status, property type, bedroom chips including Studio, **log-scale** AED price slider, radius search that uses `exact` pins only.

Precision is visible: `exact` solid marker; `community` / `area` hollow marker whose popup says "Approximate location (community centroid)". Header counts per emirate and per precision. A pin carries only the properties named in the exporter's `ALLOWED_PROPERTIES` list; a new sheet column reaches the page only when someone adds it there on purpose. `Entered By`, permit numbers, escrow agents, `Payment Plan` and `Source Licence` are never exported.

The page loads Leaflet and markercluster at pinned versions with Subresource Integrity (SHA-384), and carries a Content-Security-Policy `<meta>` that allows only itself, cdnjs, the OSM tile host and `fetch` to itself, with its one inline script and one inline style pinned by SHA-256 hash. `tests/test_site_html.py` checks that each hash matches its block byte for byte, so an edit to either block that leaves the hash stale fails a test (and would stop the page working); change the block and the hash together.

Which rows become pins (`export_map_pins._coordinate_problem`): both coordinates present and inside the coarse box that holds both emirates (`UNION_BBOX`), the registry's emirate exactly `Dubai` or `Sharjah` (never repaired or guessed from the point), and the point strictly inside that emirate's polygon (`point_in_emirate`; a point exactly on the boundary line is inside neither). This is the last stop before the public file, so it applies to a geocoder result, a `Geocode_Overrides` pin and a hand-typed coordinate alike. Every other row is counted in `meta.dropped` under one of `no_coordinates`, `half_written_coordinates`, `out_of_range`, `unknown_emirate`, `outside_emirate`, or, for a second row with the same project key, `duplicate_key`; the log gets the counts and never names a row. A blank `Location Precision` with coordinates is exported as `unknown` and drawn as approximate.

Contact data. The only analyst-typed free text that is exported is `Handover`, and it is left out when it is over 60 characters or looks like contact data: an `@`, `http:`/`https:`, `www.`, an `(at)` or `dot com` spelling, anything dotted like a host name, or a phone-number-shaped run (9 or more digits, or 7 or more after a `+`). The test runs after Unicode NFKC folding with invisible format characters removed, so a full-width `@` or a zero-width space inside a number does not hide it. Names of people and digits spelled out in words cannot be recognised and are not filtered: free text in the sheet is analyst-reviewed before it is published (a known limit). Registry text (name, developer, area and so on) is passed through with control and bidi-override characters removed, whitespace collapsed and a length cap, with no contact test.

Listing facts (price, price per sq ft, bedrooms, property types, `Handover`, `As Of`) are exported only together with an http(s) `Source URL` that is safe to publish (`sanitize_public_url`); a fact whose source cannot be shown is not shown. The link is cleaned first: a username and password are removed, and so are query or fragment parameters whose name looks like a secret (`key`, `token`, `secret`, `password`, `signature`, `auth`, `session`, `code`, `otp`, `X-Amz-...` and similar) or a person (`phone`, `mobile`, `email`, `whatsapp`, `contact`, `cell`, `agent`, `tel`), or whose decoded value is an address, a chat link, a `tel:`/`mailto:`/`whatsapp:` link or an international number (percent-escapes are decoded up to four layers deep). The whole link is withheld, and the facts with it, when its host is a chat or contact-link host (`wa.me`, `wa.link`, `whatsapp.com`, `t.me`, `telegram.me`, `telegram.dog`, `m.me`, `signal.me`, also with a trailing dot or in full-width spelling) or the path names one; when its path holds a phone-number-sized run of 9 or more digits or an address; when its host is not one a public visitor can reach (an address that is not global, a name with no dot, a reserved private top-level name such as `.local`, a short numeric spelling); or when it is over 2000 characters, has control characters, is not http(s) or cannot be written as UTF-8.

Numbers are whole numbers only. A price above AED 10 billion (`MAX_PRICE_AED`), a price per sq ft above AED 100,000 (`MAX_PRICE_PER_SQFT_AED`; these ceilings are sanity checks, not claims about the market: they refuse an extra digit, or a total such as a villa price pasted into the rate column, which would also stretch the page's price slider) and a bedroom count above `MAX_BEDROOMS` (20) are left out, and a range that runs backwards (price from above price to, bedrooms min above max) loses both ends. The page applies the same ceilings again when it reads a pin, and a test keeps its constants equal to the exporter's. A listing joins a row on ANY of its identity keys, with the latest `As Of` winning and one record used whole, and a `name:` key shared by several different registry projects joins no listing (section 3). Every string is HTML-escaped; only `http(s)` URLs are allowed in `href`. `export_map_pins.build_geojson` stays a pure function (no clock, no input mutation, identical output for the same rows in any order), keeps GeoJSON `[lng, lat]` order, and the CLI writes the file atomically. With `--min-pins N` a map with fewer pins is an error and an existing file is left untouched; the CLI exits 1 without `SPREADSHEET_ID` unless `--allow-sheet-by-name` is given.

## 8. CI (`.github/workflows/daily_uae_real_estate.yml`)

Name `Daily UAE Real Estate Scraper`; cron `0 3 * * *` (UTC; 07:00 GST); `workflow_dispatch`. Steps: checkout, Python 3.12, install, **the test gate check (`python -m scripts.check_test_gate`)**, **`pytest` (a failing test blocks the run)**, `python -m src.main`, export pins (with `--min-pins 1` while `DEPLOY_MAP` is on, so an empty map is never published), and (only when repository variable `UPLOAD_SNAPSHOT == 'true'`, default off) upload the JSON snapshot artifact. The repo is **public**, and artifacts and Actions logs of a public repo are readable by anyone. Public hosting of the map on GitHub Pages is decided (27 October 2026), but the DLD licence is still unclarified (section 10): so CI publishes no registry data anywhere until the owner sets `DEPLOY_MAP` once real data flows, and the sheet stays private.

**Test gate** (`scripts/check_test_gate.py`, the step `Check the test gate`, which runs after the install and right before `pytest`). A green test step proves something only if the suite really ran, and `python -m pytest` exits 0 after running nothing when a setting says so: `--collect-only` or `--ignore` in the `addopts` of `pytest.ini`, a `conftest.py` that skips or deselects tests, a `PYTEST_ADDOPTS` variable, deleted test files, a `pytest.toml` that takes over the configuration. The in-suite guard described under "Repository hygiene" below watches the same files, but a change to the suite can disarm it, so the gate runs from outside the suite, as a step of its own. It takes no argument, imports only the standard library and holds no secret: the step has no `env`, no `with`, no `if` and no `continue-on-error`, and `tests/test_workflow.py` pins that and the step's place in the order. It exits 1, and the job stops before any test or credential, unless all of these hold: `pytest.ini` is the expected file (`testpaths = tests`, `pythonpath = .`, `addopts` absent or holding nothing but `-q`), read with a strict grammar of its own that takes only comments, the `[pytest]` header and those option lines, each once; no `conftest.py` exists anywhere outside `.git` and `.venv`, nor any of `pyproject.toml`, `tox.ini`, `setup.cfg`, `pytest.toml`, `.pytest.toml` and `.pytest.ini`; no environment variable whose name starts `PYTEST_` is set; at least `MIN_TEST_MODULES` (23) `tests/test_*.py` modules exist; and a collect-only run (`python -m pytest --collect-only -q`, with the project's own configuration, a clean environment and a 10-minute limit) collects at least `MIN_COLLECTED_TESTS` (5200) tests. That run happens only when the static checks have passed. The floors sit just under the suite as it is today (24 modules and 5269 tests when this was written), so deleting a whole test module trips them: raise them when the suite grows, treat a drop below them as the thing to look at, and treat lowering them as a change for a reviewer, never as a way to get a green run. Its output obeys the log policy below. Every line starts `test gate: ` and holds a fixed phrase, a count, a line number of `pytest.ini` or one of the fixed file names above, and never a line of any file, the name or value of a `PYTEST_*` variable, a path or a word of pytest's own output. Success is `test gate: ok (N test modules, M tests collected)`; a failure of the gate itself is `test gate: the gate itself failed (ClassName)`. Limits, stated so that nobody assumes more: it guards against a mistaken or careless change, not against someone who means to disarm it; it shows that the suite is collected and run, not that its tests assert anything, and a tree that shadows an interpreter module (a root-level `subprocess.py` or `pytest.py`), exits early or empties the assertions still passes it; it runs in the same job and checkout as the code it guards, so a change that edits the gate, the workflow or `requirements.txt` together with the tests is caught only by review (hardening notes (a) and (b) below); and a pytest plugin that arrives through `requirements.txt` loads in the collect-only run and in the real run alike, so one that skips tests only at run time is not seen.

**Log policy** (the contract for every line the code logs; the README states the same). A public log may hold counts, source and backend names, field names, row numbers, HTTP status codes, a provider's fixed status token (`PERMISSION_DENIED`, `OVER_QUERY_LIMIT`), fixed phrases, and the class name of an exception. For an answer the code does not recognise, the field names are a count of its top-level names plus those of them that are in `sources.base.ENVELOPE_KEYS`, a list the code defines (`describe_keys`); any other name is never shown, because an answer keyed by project name has project names for keys. A Gemini finish or block reason is shown only when it has the shape of an enum name (`[A-Z][A-Z0-9_]{0,39}`) and is the fixed phrase `unrecognised value` otherwise (`gemini_news._enum_text`). The log never holds a response body, a provider's error text, a query or a URL with one, a project key or name (a key carries a registry number or developer and project names), a row's contents, a cell value, a spreadsheet title, a service-account email or any other identifier from the key file, a key or other secret, or the message text of an exception the code did not plan for.

**Who may speak** (`src/log_policy.py`, used by `src/main.py` and by `scripts/export_map_pins.py`, so the pin export follows the same policy as the scrape step). The log handler lets through only records from this project's own loggers, `src.*` and `export_map_pins`, at every level. The record of any other logger is dropped, with its traceback text. That covers urllib3 (it logs the request URL, so a search query that holds a project name, and raw header bytes), google-auth (its background lookups log retries with the service-account email in the URL), gspread, requests and the Gemini SDK (which can repeat a response body). A list of library names would lag behind the next dependency; a rule about who is speaking does not. The root logger also sits above `CRITICAL`, so a foreign record is not even created, and Python warnings are routed into logging (`logging.captureWarnings`) so that they meet the same rule instead of reaching stderr directly: google-genai warns with a value the server sent, and the `py.warnings` logger is not one of ours, so those warnings are dropped as well. What an own record says is then scrubbed once more by `SecretFilter`: the known secret values (every hidden `Config` field, the geocoder contact, the secret-looking members of a JSON secret), credential-shaped text, and the identifiers a service-account key carries: its email (with its name part and its domain), the project id, the key id and the client id. A value shorter than six characters is not treated as an identifier, because replacing it would mangle ordinary words. An exception attached to an own record is reduced to scrubbed text. What counts as a secret member of a JSON secret is decided once, in `log_policy.json_secret_members`, and the geocoder's own scrubber for provider text starts from the same rule, so the two cannot drift apart; a JSON value too deeply nested to parse counts as no key file and stops nothing. The code never relies on the scrubber; it is the last line of defence.

How the code keeps to the contract itself: `main.describe_error` logs an unplanned exception as `ClassName (at file:line in function)` and keeps the scrubbed message only for this project's own error types (`SourceError`, `SheetError`, `GeocoderConfigError`, `SetupError`, `RegistryChanged`, `SeedFileError`); the private `Scrape_Run_Logs` notes call it with `private=True`, which keeps the scrubbed message of any other error too. A library's error text is replaced where it is caught: the Gemini client's failure is shown as its class, an HTTP status code when it has one and a fixed hint (`gemini_news._describe_failure`; also when the client cannot be created), a Google Sheets API failure as `HTTP <status>` plus Google's fixed status token (`SheetManager._api_text`), an HTTP-layer failure as its class, a failed progress flush as its class. Text a person can edit in the sheet or the seed file does not travel into the log: the `Sources` cell of `Scrape_Run_Logs` is reduced to `config.SOURCE_NAMES` (section 3), and a seed CSV header problem names the missing layout columns and the header's cell count, never a header cell. The pin export turns a failure to read the sheet or to write the file into an `ExportError` whose message holds the exception class only (`reading the sheet failed: ClassName`, `writing PATH failed: ClassName`, where PATH is the `--out` argument as typed) and logs that message; a `--min-pins` shortfall is logged as counts (`only N located pin(s), fewer than the required M`, the project count and the `dropped` counts by reason); any other failure is logged as `export failed: ClassName (at file:line in function)`. What the logger does not enforce, and review and tests do: that the texts of the project's own error types and the adapters' result notes stay counts, field names and fixed phrases. The scrubber catches secrets, not content.

An exception nobody catches. Both entry points catch `Exception` and report it as described above, but a `KeyboardInterrupt` is not an `Exception` (Ctrl-C at a terminal raises it and, the code assumes, so does a cancelled run), and a few statements of `main()` sit outside its `try` blocks. Python's default hook would print the traceback and the whole `__cause__` and `__context__` chain with every message, and a chained message can carry a keyed URL or a project name. So the first statement of `main()` in `src/main.py` and in `scripts/export_map_pins.py` is `install_excepthook()` (`src/log_policy.py`), which makes `log_policy.excepthook` the `sys.excepthook`. Whatever then escapes `main()` leaves one line on stderr, `ClassName (at file.py:line in function)`, naming the innermost frame by its file name only (`ClassName (at unknown)` when there is no usable traceback), and nothing else: no message, no chain, no directory. The hook never raises, even with a closed or missing stderr, and the installer sets `sys.excepthook` and nothing else. It is called from `main()` and never at import time, so importing the modules, or running the tests, changes nothing. What it does not cover: a `SystemExit` (the interpreter exits on it without calling the hook, and prints a non-integer exit value itself; argparse's usage error in the pin export is the one that exists, see the limits below), an error raised while the modules are imported, before `main()` has run, an exception in another thread (`threading.excepthook`), and an unraisable exception (`sys.unraisablehook`).

No setting is echoed as typed. The start-up `config NAME: value` lines come from `Config.describe()`: a key or other secret, the spreadsheet id and the geocoder contact show only `set` or `not set`; the share list shows `N address(es)`; the sheet name and the User-Agent show `default` or `custom (not shown)`; `GEMINI_MODEL` shows its text only when it has the shape of a Gemini model id (otherwise `custom (not shown)`); `REQUIRE_SOURCES` shows the source names this scraper has plus a count of any other name; and only a yes/no, a number or a fixed choice that the code has already parsed and checked (the `ENABLE_*` flags, the budgets, `GEOCODE_BACKEND`, `SHARE_ROLE`) shows its value. `DEPLOY_MAP` is parsed (so a malformed local value is warned about) but not printed: the scrape step is never given it, so a `false` there would say nothing about the deployment. The warning for a yes/no, number or choice setting that cannot be used names the setting and never what was typed: `NAME is not a boolean; using <default>`, `NAME is not an integer; using <default>`, `NAME is below the minimum <min>; using <default>`, `NAME is above the maximum <max>; using <max>` (the one setting with a ceiling is `GEOCODE_TIME_BUDGET_SECONDS`), `NAME is not one of <allowed values>; using <default or auto>`, where the default, the maximum and the allowed values come from the code. GitHub prints the value of every repository variable a step receives in the step header of a public log, whatever the code does, and masks only secrets. That is why `GEOCODE_CONTACT` is a secret, why `GOOGLE_SHEET_NAME` and `GEOCODE_USER_AGENT` are local-only and not passed by the workflow at all (section 9), and why anything personal belongs in a secret.

The workflow never passes `-v`, and the only debug lines the code has are a fixed rejection word from the geocoder and the address and offset of each Dubai registry page request. Limits that remain, stated so that nobody assumes more: a service-account key read from the local file `GCP_SERVICE_ACCOUNT_FILE` does not register its identifiers with the scrubber (CI uses the `GCP_SERVICE_ACCOUNT_KEY` secret, which does); no code of this project logs with `exc_info`, but if one did, the traceback would be emitted as scrubbed text, and only the scrubber would vouch for its content; and text a person types on the command line can be echoed back at the terminal (an argparse usage error, and the `--env-file`, `--out` and `--min-pins` values), which the workflow avoids by passing only fixed arguments. The policy covers what the workflow runs. Two local tools are outside it because no workflow step runs them: `scripts/dedupe_sheet.py` prints project keys by design (it is run by a person at a terminal; it still shows an error's text only for its own error types, `SetupError`, `BackupError` and the sheet client's `SheetError`, and prints any other error as `ClassName (at file:line in function)`), and `scripts/fetch_emirate_polygons.py` (a one-off helper) prints its own `BoundaryFetchError` text, which names relations, the lookup address and counts, and only the class name for an `OSError` or `ValueError`.

The workflow file is checked by `tests/test_workflow.py` as an **allowlist**, not a list of bad commands: `workflow_problems` accepts only the known steps with their known command, action, options and environment names, and each secret only in the `env` of the two steps that need it, so a step nobody planned for (a second install, a write to `$GITHUB_ENV`, a wrapped shell, a `PYTHONPATH`, a `-v`, an `ACTIONS_*` name) is a problem by itself; adding a step or an environment name means adding it to the constants in that test on purpose. The gate step must come after the install and right before the tests, with the plain command and no `env`, `with`, `if` or `continue-on-error`, so it cannot be skipped, softened, made conditional or handed a secret. Three details are exact on purpose. The `concurrency` group must be exactly `daily-uae-real-estate` with `cancel-in-progress: false`: a different name, or an expression such as the run id, gives each run a queue of its own, so two runs could race for the sheet or the Pages deployment, and a run must never be cancelled mid-write. An environment name of the `PYTEST*` family (`PYTEST_ADDOPTS`, `PYTEST_PLUGINS`, `PYTEST_DISABLE_PLUGIN_AUTOLOAD`) is refused at the workflow, job and step level, like `PYTHON*`, `PIP_*`, `LD_*` and `NODE_*`, because it can narrow or replace the tests or change which code loads next to the secrets (the gate step refuses one in the runner's own environment as well). The scrape job has no `environment:` key (an owner decision, see the hardening notes below); only the deploy job names one, `github-pages`. A long list of deliberately broken copies each must produce its matching problem, which is what shows the checker can fail.

**Repository hygiene** (`tests/test_repo_hygiene.py`, with `tests/test_no_legacy_leak.py` for the earlier market's terms; both run in the same pytest step as everything else). Every file git would add, tracked or untracked and not ignored, is read before a push. It must be UTF-8 text without a byte-order mark and without a literal invisible or bidi-override character (write such a character as an escape), and no file may be over 1 MB. The detectors flag private-key blocks, service-account key files, cloud and chat tokens, URLs with credentials or `key=` values, absolute local paths and real-looking email addresses, and the shapes this project's own data and credentials take: a Google document or Drive URL with an id of 25 or more characters, a `SPREADSHEET_ID` value of 30 or more, a `Bearer` token of 20 or more, a run of 40 or more hex digits, a public (globally routable) IPv4 address, a `+971` or `00971` phone number with seven or more further digits, and a property-portal host anywhere outside `docs/`. An obviously fake placeholder is accepted for the Google id, `SPREADSHEET_ID`, Bearer and hex detectors only; the address, phone and portal detectors have no placeholder allowance, so a documentation example in a code comment needs a reserved address or a different example. A failure message names the file and the kind of match, never the matched value, because it would be printed in a public log. The data files are an allowlist: `src/data/` may hold only `area_aliases.json`, `emirate_polygons.geojson`, `seed_projects.csv` and `seed_registry.csv`, and a data file with a suffix such as `.csv`, `.tsv`, `.xls`, `.xlsx`, `.parquet`, `.db`, `.sqlite` or `.sqlite3` is refused anywhere else except `tests/fixtures`. The configuration of the test run is guarded too, because the workflow's test step is a plain `python -m pytest` and what it collects and how it runs are decided by files in the repository: `pytest.ini` must be a single `[pytest]` section with `testpaths = tests`, `pythonpath = .` and, at most, an `addopts` that holds nothing but `-q`; no `conftest.py` may exist anywhere (it can skip, deselect or rewrite any test); and none of `pyproject.toml`, `tox.ini`, `setup.cfg`, `pytest.toml`, `.pytest.toml` or `.pytest.ini` may exist (in pytest 9 even an empty `pytest.toml` takes precedence over `pytest.ini`, which would then go unread). A change to the suite can disarm this guard, so the test gate step (above) checks the same files again from outside it. `tests/test_no_legacy_leak.py` scans text files outside `docs/` for generic legacy markers only (place names, the old regulator, the old currency words and sign, and the old time-zone and currency codes as whole words); it names no person and no company, and a test keeps it that way.

GitHub's own debug logging (the repository secret or variable `ACTIONS_STEP_DEBUG` or `ACTIONS_RUNNER_DEBUG`, or "Enable debug logging" on a re-run) is outside the project's control; leave it off on a public repo. The geocoding time budget is `GEOCODE_TIME_BUDGET_SECONDS`, default 3300 s (55 minutes) and at most 4500 s (75 minutes), inside the 90-minute scrape job limit (section 5). The keys a person needs, such as the unmatched `Listing_Data` keys or the registry rows whose analyst-added column values were not carried over, are written to the `Notes` of the private `Scrape_Run_Logs` row. The Pages artifact and the `deploy-map` job run only when repository variable `DEPLOY_MAP == 'true'` (default off: public GitHub Pages hosting is decided, and the owner turns it on once real data flows). Public-repo note: GitHub disables scheduled workflows after 60 days without repository activity. Minimal permissions; one `concurrency` group so runs queue (exact name above); a `timeout-minutes` on every job (90 for the scrape, 15 for the deploy). The workflow uses only GitHub's own actions, pinned to a major version tag (checkout v6, setup-python v7, upload-artifact v7, upload-pages-artifact v5, deploy-pages v5: the Node 24 majors, since GitHub removed Node 20 from its runners in September 2026), not to a commit. `GEOCODE_CONTACT` is a **secret**, not a variable, because the value of a variable is printed in the public step log and a secret is masked.

**Hardening that is an owner decision and is NOT implemented.** These are known, accepted for now, and listed so that nobody assumes the workflow already does them. (a) *Dependencies.* `requirements.txt` uses open `>=` floors, there is no lock file and no hashes, and the install runs in the same job that later holds the secrets, so a hijacked or yanked release of any dependency would run next to them. The same goes for a pytest plugin that arrives through `requirements.txt`: it loads in the gate's collect-only run and in the real run alike, and the gate's floor on collected tests does not see it skip tests at run time. The fix is `pip-compile --generate-hashes` to produce a hashed lock file, `pip install --require-hashes -r` that file in the workflow, and Dependabot (the `pip` and `github-actions` ecosystems) to propose each bump as a reviewed pull request; it needs a matching change to the pinned install line in `tests/test_workflow.py` (`COMMANDS["install"]`), which today accepts only `pip install -r requirements.txt`. (b) *Who can reach the secrets, and who can change the checks.* The secrets are repository secrets, and any branch that someone with write access dispatches can read them. The test gate, `pytest.ini`, the tests and the workflow live in the repository they guard, so one pull request can weaken them together, and only a reviewer notices. Protect `main` with a ruleset (no direct pushes, reviewed pull requests), keep the list of collaborators minimal, consider a CODEOWNERS file for `.github/`, `scripts/check_test_gate.py`, `pytest.ini`, `requirements.txt` and `tests/` with "Require review from Code Owners" switched on, and optionally move the secrets into a GitHub Environment restricted to `main` and name it in the scrape job; that needs `environment` added to the scrape job's allowed keys in `tests/test_workflow.py` (`JOB_KEYS`), on purpose. (c) *Actions pinned to major tags, not commit SHAs.* A tag can move; this is an accepted risk, and Dependabot would turn each bump into a reviewed pull request. (d) *A keyed geocoder brings its terms to the map.* If `DEPLOY_MAP` is on and the geocoder is LocationIQ, Geoapify or Google, the published pins are that provider's results and its attribution and terms apply to the public map. The map credit names OpenStreetMap only, and Google's terms restrict displaying its results on a map that is not Google's, so keep Google off a deployed map (it is opt-in already, section 5). (e) *The first commits publish the committer's identity.* Use GitHub's noreply address for the git author (GitHub shows it under the account's email settings, with an option to block pushes that expose a private address) before the first push.

## 11. Test policy

- Tests are ported with the code, not after. Fixtures are **synthetic and labelled** (`# SYNTHETIC`): no real registry data is committed. The one deliberate exception is the ground-truth table of public place coordinates in `tests/test_emirates.py`: real places, used only as an accuracy yardstick for the emirate polygons, never registry data, never published. Its provenance is recorded per row: every named place is an OpenStreetMap feature looked up by name through the Overpass API on 25 Oct 2026, the row keeps the feature's OSM element id (`osm`, so it can be looked up again) and its position rounded to 5 decimals, and only five round-number points (open water, latitude and longitude 0, empty desert) have no element because they come from no source. No row was copied from a property portal, an encyclopedia, a search engine or a geocoding service. A test fails if a row without an `osm` id is a Dubai or Sharjah row, has a coordinate with more than 2 decimals, or is a sixth such row (and if any row has more than 5 decimals, repeats another row's element id or coordinate, or has an element id that is not of the form `n<id>`, `w<id>` or `r<id>`), if a label is not plain ASCII, if that file names one of the sources the table must not use (two property portals, an encyclopedia and its data project, or a project brief), if the docstring loses the OSM credit, if a precise coordinate is hard-coded anywhere else in the file, and if a `border_sensitive` flag (a point within about 300 m of the nearest polygon edge, where a surveyor-grade border could disagree with OSM's) does not match the distance to the bundled border. The expected emirate of each Dubai or Sharjah row is the plain fact about the place, not the output of `src/emirates.py`; all fifty of them were also run once through Overpass `is_in` (a manual, networked step outside the test suite whose output is not kept; it reads the same OSM relations the polygons were built from, so it checks the polygon code and its simplification, not OSM's border itself), and `OVERPASS_CONFIRMED` lists exactly the keys it covered. The table does not audit OSM's border against official survey data. The ODbL credit and this method sit in that file's docstring. `docs/research-2026-10-25.md` is the record of the research session's one-off exploratory measurements, among them its own check of 16 hand-picked points with `is_in` and its sample of 36 project names; their reference points are not kept, and the note's Correction block says that it holds no property-portal data and is not a data source. Nothing in this repository reads it, the test table uses no coordinate from it, and no portal or encyclopedia coordinate is to be added to this repository (property portals forbid automated access, section 0 rule 4).
- `tests/test_no_legacy_leak.py` fails if any tracked or untracked-but-not-ignored text file outside `docs/` contains a generic marker of the earlier market: a place name, the old regulator, a currency word, the rupee sign (also as a JSON `\u` escape or an HTML character reference), further legacy city words (the list is `FORBIDDEN_SUBSTRINGS` in that test), or, as whole words, the legacy time-zone and currency codes. The test names no person and no other company, even to forbid them (this repository is public), and a test of its own keeps it that way.
- `tests/test_check_test_gate.py` tests the gate script (section 8): each way to make the test step pass without the suite must turn it red, its messages hold fixed phrases and numbers and never echo a line of a file or a word of pytest's output, what it accepts in `pytest.ini` is checked against what pytest itself reads, and the real tree must pass it, also in a real process. `tests/test_log_policy.py` tests the uncaught-exception hook (section 8): a class-and-place line and nothing else, never raising, nothing installed by an import, and real interpreters in which both entry points are interrupted.
- Generic suites kept from the earlier scraper (adapted): geocoder backend selection / 429 abort / queue ordering / cooldown, sheet sharing, row deletion, dedupe clustering, seed upsert, export-pins structure.

## 12. Module interfaces (build-out contract, written 25 Oct 2026)

The foundation (`src/config.py`, `models.py`, `areas.py`, `listing_data.py`, `emirates.py`) is built, reviewed and frozen: **import from it, do not edit it**. If a foundation function is wrong or missing, say so in your report (`open_issues`) instead of patching it. Everything below is owned by exactly one builder; no builder edits a file it does not own.

General rules for every module:
- No network and no credentials in tests. HTTP goes through an injectable `requests.Session`-like object (`session=` argument) so tests pass a fake. Fake secrets in tests are obviously fake strings such as `"fake-key"`.
- Never print, log or put in an exception message a secret value (API keys, tokens, the service-account JSON, an `Authorization` header). Log `cfg.describe()` style "set / not set" only. Never put a response body, or a provider's own error words, in an error or a log line: state the HTTP status, the response size and a fixed phrase, or a fixed status token (`HTTP 403 PERMISSION_DENIED`), because a server's error page can echo the query, a query is a project name, and the Actions log of a public repository is public. Where the code can avoid an exception's own text (it can carry a request URL or row content), it names the exception class instead, as the HTTP helper (`send_with_retries`), the geocoder flush, the Gemini client and the pin export do; section 8 states the log policy (only this project's own loggers reach the public handler, and every library's records are dropped), including the one place that still prints scrubbed text (this project's own error types). Log lines carry counts, source and backend names, field names, row numbers, status codes, fixed phrases and exception class names, never a cell value or a project key.
- Timestamps via `models.utc_now_iso()`; dates `YYYY-MM-DD`; display via `models.format_dubai_time`.
- Sheet access only by header name. Write ids and keys as RAW strings (never `USER_ENTERED`) so leading zeros and `name:` keys survive.
- Use the standard `logging` module; no `print` outside `if __name__ == "__main__"` CLI helpers.

`geocode_pending` returns new rows (use `model_copy(update=...)`; never mutate the input). Order of work: (1) apply `Geocode_Overrides` matched on ANY of a row's `identity_keys()` (always, even when `cfg.geocode_enabled` is false or the backend is exhausted), method `override`; (2) skip rows that already have coordinates; (3) if geocoding is disabled stop; (4) queue = never-tried first (blank `Geocode Status`), then stalest `unresolved` older than `cfg.geocode_retry_cooldown_days`; (5) per row walk `row.geocode_tiers()`, validate every hit as in section 5, first passing tier wins and sets `location_precision`, `geocode_method` (`<backend>`), `geocode_status` (`resolved via <backend> <tier> <YYYY-MM-DD>`, plus ` border-check` within 1.5 km of the other emirate); (6) a row with no passing tier gets `unresolved <YYYY-MM-DD>` and **no coordinates**; (7) stop on `cfg.geocode_max_per_run` (0 = backend default: nominatim 200), `cfg.geocode_time_budget_seconds`, or the first 429 / daily-quota response (abort, record `aborted`, cache nothing as a false miss); call `flush(rows_so_far)` every `cfg.geocode_flush_every` resolved rows.

### `src/main.py` (owner: main builder, built after the above exist)
`run(cfg, *, adapters=None, sheets=None, today=None, geocode=geocode_pending) -> int` returns the exit code; `main(argv=None) -> int` loads config, builds the real objects, and calls `sys.exit` only under `__main__`; its first statement is `install_excepthook()` (section 8). Flow: log `cfg.describe()` and `cfg.warnings`, then `sheets.open()`, then read registry, overrides, listing records and previous counts, then apply the listing seed, then for each adapter: skip or disable with logging (`SKIPPED (not configured)`; a skipped adapter named in `REQUIRE_SOURCES` is a failure), `fetch()`, `check_row_count`, record `SourceRunInfo`; one failure does not stop the others. Then `dedupe_rows(fresh + existing)` (fresh first), `geocode`, write registry, candidates and Map_Pins, and `append_run_log` (always, best effort, even on failure). Every registry write goes through one `RegistryWriter` guard (the geocode flush included): it refuses on a dry run, on unreadable or unusable rows, and on a failed merge, and, because `write_registry` replaces all data rows while a run can last most of an hour, it re-reads the tab first and refuses (exit 1, nothing written) if it no longer matches what the run last read or wrote, so a row a person typed in the meantime is never deleted. The row-count shrink guard applies only to sources with `expects_rows`. The exit code is non-zero if any enabled adapter failed, a required source was skipped, or the geocode stage crashed or aborted for a reason other than a quota (a refused key, five failed lookups in a row). A geocode run that `aborted` on a quota (HTTP 429, Google over-limit) with rows still pending is **not** an error; it is logged as a warning. An exception is reported through `describe_error` (section 8), so one the code did not plan for shows its class and place, never its text; only this project's own error types, such as `SetupError`, show their (already scrubbed) text. One that nothing catches (a `KeyboardInterrupt`, say) is printed by the hook that `main()` installs first, in the same form.
