## Dubai official data

Dubai has no fully open, keyless, daily flat file or API equivalent to the K-RERA registry, but the authoritative complete register does exist: the Dubai Land Department (DLD) "Real Estate Projects" dataset from its TABU system, keyed by project_number and developer_number. The best primary route is the Data.Dubai open API (https://apis.data.dubai/open/dld/dld_projects-open-api). It answered 401 without a key, so the route exists but I could not pull rows. It needs a free Data.Dubai portal account and an API key (key plus secret, then a client_credentials Bearer token), and supports limit, offset, order_by, filter and column. DLD updates the source on each transaction but the platform copy is published monthly, so "daily" is not achievable from official open data; the anonymous Data.Dubai catalogue API (https://data.dubai/o/c/datasets) can be polled for dateModified to detect changes. DLD's own Open Data page serves the same projects data with a few extra fields (escrow account number, project value, inspection date) but only through a reCAPTCHA-gated POST gateway, so it is not safe to automate. Dubai Pulse, the old CKAN-style source with a plain projects CSV, is decommissioned and redirects to data.dubai; only Wayback copies survive, and they give the exact 37-column schema. The live row count could not be verified; file sizes (1.77 MB in May 2024, 2.28 MB in Nov 2025, about 850 bytes per row) suggest roughly 2.5k to 4k projects, and the catalogue's "expected volume 24865" looks wrong. Developers (about 1,259 per catalogue), escrow agents, an area lookup and a permits dataset sit in the same DLD family on Data.Dubai. Per-project Mashrooi data is API-key gated, and the Trakheesi permit validation API is paid (AED 30,000 + 5% VAT a year). There are no coordinates, prices or unit mixes anywhere in the DLD project data, so geocoding needs the DLD area id mapped to a Dubai Municipality community polygon centroid, or Nominatim. Licensing is the main open risk: the catalogue says "Not Specified" and the site terms point to non-commercial use, so get written clarification from DLD or Data.Dubai before commercial use.

**Schema implications**

- Dedup key: replace the K-RERA registration number with a namespaced composite key (emirate = Dubai, registry = DLD, dld_project_number). Keep dld_project_id (internal surrogate) as a secondary id. project_number values are small integers (for example 913), so never use them without the emirate prefix.
- Developer key: dld_developer_number (and dld_master_developer_number), plus developer licence number and expiry from the developers dataset.
- Name columns: project_name_en and project_name_ar, master_project_en and master_project_ar, area_name_en and area_name_ar. The old export is mostly Arabic, so do not dedup on name.
- Status columns: project_status (for example ACTIVE, FINISHED, CANCELLED; only FINISHED was seen), percent_completed, project_start_date, project_end_date, completion_date, cancellation_date, adoption_date and inspection_date. The legacy CSV uses dd-mm-yyyy, so normalise to ISO.
- Escrow columns: escrow_agent_name (in the register), escrow_account_number (portal only, nullable), project_value (portal only, nullable).
- Location columns: dld_area_id, dm_community_number (via the dld_lkp_areas bridge), zone_en/ar, zoning_authority_en (such as DDA/DMCC free-zone authorities), master_project_en. Add lat, lng, geocode_method (dm_community_centroid, nominatim, manual) and geocode_confidence, because DLD supplies no coordinates.
- Scale columns: no_of_lands, no_of_buildings, no_of_villas, no_of_units.
- Price columns must be nullable with a price_source field, since the official register carries no prices.
- Provenance columns: source_dataset_id (467654), source_refresh_date (catalogue dateModified), fetched_at, licence_note, row_hash. The platform replaces records monthly, so keep a status-history table rather than overwriting.
- Optional permit linkage (per listing, not per project): trakheesi_permit_number, rera_orn or brn, ded_licence_number. Nullable and not a dedup key.
- Registry namespacing: store registry and registry_id so Sharjah (its own registry) can coexist with Dubai without key collisions.

**Gaps (looked for, not found / not verified)**

- Live row count of the DLD project register could not be verified (dataset API is key-gated and the DLD portal is reCAPTCHA-gated). Estimate only: about 2.5k-4k from legacy CSV size. The catalogue 'expected volume 24865' contradicts the file sizes.
- The Data.Dubai API key flow (account, access-key request form, approval time, rate limits, actual column names in the new API) was not tested, because registration was out of scope. 'Free' is inferred from the FAQ, which states no fee for open datasets.
- No coordinates exist in any DLD project, land, building or unit schema. Only community-level polygons (Dubai Municipality KML) are available; project-level points need Nominatim/OSM or manual work.
- No prices, price lists, unit mix, launch dates or handover-payment plans in the project register. Project value appears only on the DLD portal tab, and escrow account number only there too.
- Daily refresh is not available from official open data: the platform copy is monthly (the source is updated on each transaction). Whether the DLD portal gateway returns full history or only a date window per query is unknown.
- Trakheesi validation: the public page needs undocumented parameters; the supported validation API is paid (AED 30,000 + 5% VAT a year). The free annual permits dataset has unconfirmed column names and no confirmed link to project_number.
- Mashrooi / Project Status Enquiry data is API-key gated; I did not test third-party claims of an anonymous guest token.
- Oqood (off-plan interim register) has no public registry; it appears only as a registration type and in partner APIs.
- Licence for the DLD datasets is 'Not Specified' in the catalogue, and the Data.Dubai terms and the Open Data Licence PDF disagree on commercial use. Needs written clarification.
- An Arabian Business article on project counts returned 403 and was skipped. Third-party project counts are filtered subsets and not a register total.
- Legacy CSV project names are mostly Arabic; whether the new API returns English names directly was not confirmed.
- No Sharjah data was examined here; that is a separate stream.

## Sharjah official data and market structure

There is no K-RERA equivalent for Sharjah: I found no bulk, feed or open-data publication of Sharjah projects from any government body, and no published freehold-zone list or escrow rulebook. The closest official thing is the Sharjah Real Estate Registration Department (SRERD) website, whose own JavaScript contains a public 'List of Projects' page. It shows project name (AR/EN), area (AR/EN) and ownership type, and is loaded by a POST call to cms-proxy.shjrerd.gov.ae/api/Projects/GetProjects. I did not call it because this task was GET-only, so row count and freshness are unverified. SRERD's GET endpoints do work, and the transaction ticker returned live area-level sales dated 21-22 Oct 2026. It has no project or developer field. Shurooq and investinsharjah.ae sit behind a Sucuri JS challenge and were not read. Portals publish project lists; their terms forbid automated access, so none is used. Launch signals come from developer sites and press (Arada's open WordPress REST API is the most structured, but Arada's terms forbid automated access, so it is reference only unless Arada gives written permission). The market is concentrated: Arada (Aljada, Masaar, Nasma, Anantara Sharjah Residences), Alef (Al Mamsha), Eagle Hills with Shurooq (Maryam Island, Kalba Waterfront), Ajmal Makan (Sharjah Waterfront), Al Zahia (Majid Al Futtaim JV with the Government of Sharjah), Tilal (plots), Sharjah Sustainable City, Shurooq's Ajwan Khorfakkan, and new entrants such as Azizi. The researcher's "single best primary" (a consumer portal's new-projects feed for daily discovery with coordinates) is withdrawn: portals forbid automated access; not used. The SRERD projects list should be tested with one approved POST as the authoritative name/area/ownership cross-check. Two corrections to the brief: Maryam Island is Shurooq plus Eagle Hills (not on Alef's site), and Waterfront City is now marketed as Ajmal Makan City.

**Schema implications**

- Replace the K-RERA registration number with a source-ID key hierarchy: srerd_project_id (proId, only if the POST test works) > name_key (normalised project + developer). Portal ids were proposed as further levels of the hierarchy; withdrawn: portals forbid automated access; not used. The existing name_key logic can be reused, but add 'emirate' to the key so Dubai and Sharjah never collide.
- Add columns: emirate (Dubai/Sharjah), city_or_region (Sharjah city, Khor Fakkan, Kalba, Hamriyah), srerd_area (the official area name in AR/EN, e.g. Muwaileh Commercial, Al Khan, Al Sehma), master_community (Aljada, Masaar, Al Mamsha, Maryam Island, Al Zahia, Tilal City, Ajmal Makan City), project_name_ar, and ownership_type (freehold / usufruct / leasehold).
- Phase handling must change: replace the Phase/Wing/Block stripper with a master -> sub-project -> phase model. Examples: Sawa 1-4, Suroor 1-4, Nama 1-4, Nasaq 1-6, Nest 1-12, Masaar 2/3, Safa 1. Dedup at the sub-project level and keep phase as its own column.
- Coordinates from portal feeds, with geocoding demoted to a fallback and validator, were proposed here; withdrawn: portals forbid automated access; not used. Geocoding stays the location source. Add geo_source (nominatim/photon/manual) and keep geocode_status. Nominatim will fail on marketing names like 'Sawa 1', so geocode on the community or area name.
- Add status fields the sources give: handover_date (quarter-year strings like 'Q4 2026'), project_status, completion_percentage, starting_price_aed, down_payment, payment_plan, property_type (add 'Plot' for Tilal). Add last_seen_date and first_seen_date, because there is no registration date to stand in for 'launch'.
- Add developer fields: developer_brand, master_developer, and a JV note. Examples: Maryam Island = Shurooq + Eagle Hills; Sustainable City = Shurooq + Diamond Developers; Al Zahia = Majid Al Futtaim + Government of Sharjah. **Schema implications**

- Dedup key: no commercial source exposes a stable regulator ID, and Trakheesi is an advertising permit that sources frame per listing or ad, so it cannot key a project. Use composite project_key = slug(emirate)|slug(master developer)|slug(project name), plus an alias table, and per-source id columns for licensed APIs only: reelly_id, opps_id (UUID). Portal id columns were proposed here; withdrawn: portals forbid automated access; not used.
- Regulator ID columns to join from the official-registry stream: regulator (DLD-RERA or SRERD), regulator_project_no, escrow_account_no. Keep a nullable permit_no with permit_type='Trakheesi ad permit', since commercial project pages are not known to show one.
- Replace K-RERA/PIN geography with emirate, city, community (e.g. Damac Islands, Dubai Creek Harbour, Aljada, Muwaileh, Sharjah Waterfront City), master_community and name_ar. The UAE has no postcode system, so community name is the geocoding anchor. Add lat, lng, coord_source (vendor / OSM geocode / manual) and coord_precision. A portal coordinate source was proposed here; withdrawn: portals forbid automated access; not used. A licensed API may supply coordinates (Reelly: vendor claim, unverified).
- Price: starting_price_aed (int), price_max_aed, price_as_of date, price_source. Use AED, not INR, and store area_unit explicitly (sq ft vs sq m).
- BHK: bedrooms_min, bedrooms_max, unit_types (Studio, 1BR to 5BR, Penthouse), property_types (apartment, townhouse, villa). Sources encode a studio differently; Danube lists 'Studio to 3BR + Penthouse'.
- Possession: handover_date (ISO) and handover_text (e.g. 'Q4-2029'), launch_date (a sales-start date, where a licensed source gives one), sales_phase, construction_phase, completion_pct, plus a stale_flag when the stated date is in the past (Binghatti Aurora page still says Q2 2025).
- Payment plan as JSON: down_payment_pct, during_construction_pct, on_handover_pct, post_handover_pct (OPPS payment_plans[], Danube '30/70'). Add ownership_type (freehold/leasehold).
- Developer normalisation table (master developer vs sub-brand/JV: Meraas to Dubai Holding, Nakheel Collection, Arada vs Aldar for Aljada buildings, Binghatti branded projects) because name drift breaks the dedup key.
- Per-row provenance and licence: source_name, source_url, licence_class (licensed-API / developer-permitted / manual), fetched_at. Publishing the public map needs redistribution rights; keep any partner-only fields (e.g. Reelly agent-only commission data) out of the sheet.

## UAE geocoding feasibility (measured 25 Oct 2026, public Nominatim, 80 requests)

Verdict: name-only geocoding with free OSM-based geocoders will NOT give a complete map; it works for communities, fails for single off-plan projects. Public Nominatim (80/80 requests used, 2026-10-25, OSM data updated 2026-10-24) plausibly resolved 15 of a sample of 36 public project names (15/36, 42%) with the best of 2 phrasings: Dubai 11/18 (61%), Sharjah 4/18 (22%). "Plausibly" was a hand judgement (right emirate and the right part of it) against reference points that are not kept; the percentages are our measurement of Nominatim, not registry data. The split is by NAME TYPE, not emirate: master communities/districts 14/21 (67%) vs single named projects (towers, clusters, off-plan launches) 1/15 (7%, only 'Avarra by Palace'). Villa/townhouse communities 7/11, but all are community-level names (Arabian Ranches, Damac Hills, Mudon, Masaar...), not individual villa projects. Bare names are dangerous: 9/36 bare queries returned confident global junk (Mudon -> Myanmar, Ovelle -> Mississippi, Aljada -> Spain, Al Mamsha -> Yemen, Tilal City -> Abu Dhabi street). Adding ', Dubai, UAE' / ', Sharjah, UAE' (or countrycodes=ae) cut wrong hits from 9 to 1, but the 1 survivor passes any bbox/emirate-name check: 'Hayyan, Sharjah, UAE' -> a street in Kalba, Sharjah Emirate, far from the real Hayyan. Photon (komoot) reads the same OSM objects (identical coordinates on shared hits; 5/8 plausible, 3 wrong incl. 'Valia Tower' -> Calgary) so a second free OSM geocoder adds nothing. Root cause is data, not tooling: Overpass confirms OSM simply lacks Maryam Island, Sharjah Sustainable City, Waterfront City, Nasma Residences, Valia, Ovelle, Palm Central, Crestlane, Meriva, Pietrus, Greenz, Damac Lagoons. Parent communities for the missing off-plan names DO exist in OSM (The Valley, Dubai Islands, Academic City, Business Bay, Dubai South, City Walk features, Palm Jebel Ali show village) and were judged by hand to sit near the real towers in the cases checked (a one-off comparison with reference points that are not kept, not run through Nominatim). No government source with project coordinates is publicly usable: DLD Project/Land/Building tables carry names, master project, area, zone but no lat/lng and are captcha-gated; Makani needs UAE PASS in its web app; gis.dm.gov.ae does not resolve. Recommended design: tiered geocode (exact project -> DLD/Sharjah 'master project' -> area/district) with a precision flag on every pin, manual override table, polygon-based emirate check, and a paid or self-hosted geocoder because public Nominatim limits scheduled scripts to 4 req/min. Expect roughly 10-20% exact pins and the rest community/area-level on a full registry (my estimate from a 15-name single-project sample).

**Emirate boundary rule**

Bounding boxes cannot assign an emirate: the Dubai emirate bbox is 85% covered by the Sharjah emirate bbox (1.34 of 1.58 deg2; computed from the two Nominatim boxes), and places on either side of the border (Al Nahda, Al Qusais and Mirdif in Dubai, Muweilah in Sharjah) lie inside both boxes, while the Kalba exclave (Sharjah) falls outside the Dubai box. A wrong match can also pass: 'Hayyan' returned a street in Kalba (Sharjah Emirate, far from the real Hayyan). RECOMMENDED RULE (layered, bbox only as coarse gate): (1) The emirate comes from the SOURCE registry (DLD area/zone = Dubai; Sharjah registry = Sharjah), never inferred from coordinates. (2) Validate the geocode by point-in-polygon against the real OSM admin polygons (relations 3766483 Dubai, 3766486 Sharjah; cache GeoJSON once, test with shapely) - checked this session via Overpass is_in on a hand-picked set of 16 points (not kept): all 16 matched the expected emirate, including the exclaves Hatta (Dubai) and Kalba (Sharjah) and border-zone points on both sides of the border (Al Nahda, Al Qusais and Mirdif on the Dubai side, Muweilah on the Sharjah side). (3) Require the provider's address state (Nominatim returns 'Dubai Emirate' / 'Sharjah Emirate') to equal the declared emirate. (4) Distance gate: reject if the point is more than ~8 km from the centroid of the project's declared area/master community (would have rejected Hayyan->Kalba) and reject street-type hits (class highway) for project queries. (5) On any mismatch do not move the project to the other emirate; mark geo_status=conflict and show at community precision. (6) Points within ~1.5 km of the shared border need a human/override check because OSM draws the border imperfectly (Al Nahda is split between the two). Use countrycodes=ae on every call and the union bbox only to discard obviously foreign results.

**Query phrasing evidence**

- Always send countrycodes=ae (verified: bare 'Aljada' returned Murcia, Spain 5,451 km away; with countrycodes=ae it returned 'aljada by arada') and add accept-language=en. Bare names produced 9 wrong hits in 36 queries (25%): Mudon->Myanmar, Ovelle->Mississippi, Le Chateau Pietrus->France, Aljada->Spain, Maryam Island->Chicago, Tilal City->Abu Dhabi, Al Mamsha->Yemen, Khalid Bin Sultan City->Pakistan, Hayyan->Yemen.
- Appending ', Dubai, UAE' / ', Sharjah, UAE' removed 8 of those 9 wrong hits (turned into empty results) and added 3 correct hits (Mudon, Aljada, Al Mamsha) with zero hits lost. Prefer an empty result to a wrong one: keep the qualified phrasing as the primary query.
- The qualifier is not enough: 'Hayyan, Sharjah, UAE' returned Obaid Bin Hayyan Street in Kalba (state 'Sharjah Emirate') far from the real Hayyan, which passes an emirate-name or bbox check. Reject class=highway for project queries and apply a distance gate to the declared area centroid.
- OSM often stores the project as '<Name> by <Developer>' (Avarra by Palace, Masaar by Arada, aljada by arada, Glamz by Danube), and Nominatim matches the shorter bare prefix ('Masaar' and 'Aljada' both hit). So query the registry's project name as given, then retry with 'by <developer>' appended or removed; stripping the developer is only evidence-backed in the direction of bare prefix matching.
- Dropping generic suffix words helped once: 'Tilal City, Sharjah, UAE' returned nothing but 'Tilal, Sharjah, UAE' found OSM's TILAL neighbourhood (n=1). Stripping 'Tower'/'Residences' showed no gain: 0/7 Sharjah and 7/8 Dubai tower or residence names were absent from OSM under any phrasing. Stripping 'Phase' was not tested.
- Spelling aliases are required: 'Jumeira Village Circle, Dubai, UAE' returned nothing while 'Jumeirah Village Circle' resolved. Al/El variants were not tested (budget). Keep a canonical alias table (Jumeirah/Jumeira, Al/El, Muweilah/Muwaileh/Muwaileh, Maryam/Mariam).
- When a single project fails, query its parent: master project or area from the registry (DLD Master Project/Area). Parents exist in OSM for 7/7 failed off-plan names checked via Overpass (Dubai Creek Harbour, The Valley, Dubai Islands, Academic City, City Walk, Palm Jebel Ali, Al Khan) and were judged by hand to sit near the real towers; show these as community-precision pins, not exact.
- Photon bias (lat/lon) turns bare 'Aljada' and 'Mudon' into correct hits but still produced Calgary for 'Valia Tower' and a hotel in Abu Dhabi for 'Tilal City', so bias is no substitute for countrycodes plus a polygon check.
- Nominatim did not index an exact-name hit that Overpass proves exists as a name-only node ('Hayyan by Alef Group'); such nodes cannot be found by name through any Nominatim-backed free geocoder (n=1).
